# M5: modules and imports

A program can now be more than one file. One file is one module, as the M0
spec's tour says, and a file uses another by importing it.

## Where this comes from

`docs/m0-spec.md` says "One file is one module" and nothing more: no
syntax, and no rules for what a module can see. Two of its programs use
another program's functions: program 10 calls `parse_port` from program 9,
and program 14 tests `chunk` from program 12. Today `examples/m0` copies
those functions into a preamble.

So modules are unfinished work from the spec, which the one rule lets in
without evidence. Their **surface** is not in the spec, and the one rule
still applies to it: M5 adds what one file using another needs, and
nothing a real program has not asked for. That means no visibility
modifiers, no `as` renaming, no importing single names, no packages and
no search paths. Each is listed under "Not in M5", with what would bring
it in.

None of the three real programs reached for imports; each fits in one
file. This milestone rests on the spec, not on them.

## The rules

**Importing.** `import "path"` names another file, without its `.fn`,
relative to the directory of the file that imports it. Like Go's imports,
it is a path, so it can name a subdirectory (`"lib/report"`) or a parent
(`"../shared/words"`). There is no search path and no configuration: the
path says where the file is.

```
import "lib/report"

print(report.line("apples", 1250))
```

- Imports go at the top of a file, before anything but comments, one per
  line.
- A path is relative. It does not start with `/`, does not end in `.fn`,
  and its last part is a valid name.
- The module's name is the path's last part: `"lib/report"` is `report`.

**Using what a module declares.** Everything a module declares at its top
level is reached through its name: `report.line(...)`. This is how the
built-in modules already work (`fs.read`, `json.parse`), so there is one
way to use a module, whichever kind it is. The qualified name works
everywhere a name does:

| Use | Written |
| --- | --- |
| a function | `shapes.area(s)` |
| a `let` | `config.rate` |
| a type | `fn f(s: shapes.Shape)`, `List[shapes.Shape]` |
| a record literal | `shapes.Size { w: 1.0, h: 2.0 }` |
| a variant | `shapes.Circle(1.0)`, and in a pattern `shapes.Circle(r) -> ...` |
| a function declared on a type | `sinks.Console.new("> ")` |

Methods need no name, because a method is found through its value:
`c.write("x")` works on a `sinks.Console` anywhere. Fields are read the
same way, `size.w`.

**Everything is visible.** A module has no private names in M5. Whether
some declarations should be private is a question for real programs.

**What a module may hold.** An imported file holds declarations (`fn`,
`type`, `interface`, `test`) and `let`s. A top-level statement or a `var`
in an imported file is an error, so the only code an import runs is what
its `let`s compute.

A module's `let`s are computed once, before anything in the program that
imports it runs. Modules are run in dependency order: a module's own
imports first, in the order they are written. A `!` that fails in a
module's `let` stops the program, as at the top level of a program.

**Programs and modules.** The file given to `fennic run` or `fennic test`
is the program; every other file is a module. A module's `fn main` is not
run, and its `test` blocks are not run, so one file can be both a tool and
a library. `fennic test chunk_test.fn` runs the tests in
`chunk_test.fn`, not those in the modules it imports.

**Each file sees only what it imports.** Importing `report`, which
imports `format`, does not let you write `format.money(...)`; import
`format` yourself. A module imported by several files is one module: its
`let`s are computed once, and its types are the same types everywhere.

**No circles.** A file cannot import itself, directly or through other
files. The error names the whole circle.

**Names.** A module's name cannot be the name of a built-in module (`fs`,
`json`, `csv`, `log`, `int`) or of another import in the same file. A
local name cannot be the name of an imported module. Two files called
`util.fn` in different directories cannot both be imported by one file:
rename one. A collision is reported where the second name is written.

**Types are nominal across modules.** A `User` declared in `a.fn` and a
`User` declared in `b.fn` are two different types, as two record types
with the same fields in one file already are. Messages name the module
when a type comes from another file: `a.User`. A value prints as it
always has, `User { name: "Ada" }`, without the module.

**Methods are declared with their type.** `fn Shape.describe(self)` goes
in the file that declares `Shape`. Writing `fn shapes.Shape.describe(...)`
elsewhere is an error that says to add it to `shapes.fn`, or to write a
plain function taking a `shapes.Shape`. This keeps every method of a type
in one place, so a reader and the checker find all of them in its file.

**Interfaces stay structural.** A type satisfies an interface from any
module if it has the methods. `sinks.emit(Shout { times: 1 }, ...)` works
when `Shout`, declared in the program, has the `write` that `sinks.Sink`
lists.

**Paths in messages.** A problem in an imported file names that file as
it would be typed from where `fennic` was run:
` --> app/lib/report.fn:3:5`. Data paths (`fs.read`, `csv.read`) are
unchanged: they resolve against the working directory, as decided in M3
round two. Only imports resolve against the importing file.

## The tools

- **`fennic run` and `fennic test`** load the program, then its imports,
  check every file, and run nothing if any file has a problem. Problems are
  reported in import order, file by file.
- **`fennic fmt`** formats `import` lines like any other: `import "x"`. It
  does not sort or move them. It formats only the files it is given.
- **`fennic lsp`:**
  - It resolves imports from the file's own path on disk. If an imported
    file is open in the editor, its unsaved text is used instead.
  - Go to definition on `report.line` opens `lib/report.fn` at `line`.
    Hover shows `fn line(name: Str, cents: Int) -> Str`.
  - On a module's name, `report`, hover shows its import,
    `import "lib/report"`, and go to definition opens the file at its
    start.
  - An imported file with problems gets one diagnostic on its import line,
    "`lib/report.fn` has 2 problems". The problems themselves appear when
    that file is opened.
  - An import that cannot be found gets the same message
    `fennic run` prints.

## Acceptance

`examples/m5/` holds what M5 must do, written before the code:

- **`programs/`.** Multi-file programs, each a directory run with
  `fennic run main.fn` from inside it, with expected output in `main.out`.
- **`rejected/`.** Multi-file programs that must be refused, each with the
  exact message in `main.out`.
- **`fmt/`.** A formatter pair for `import` lines.
- **`lsp/`.** Two scripted sessions over a small project on disk.

The 34 examples, the 45 rejected programs, the 20 spec programs, the three
real programs and all of M4's cases must still pass.

**Spec programs 10 and 14 stay as they are.** They call `parse_port` and
`chunk` without a module name, as the spec wrote them. With imports, a
preamble could import program 9 or 12, but it could not make those
unqualified calls work. `examples/m5/programs/04_tests_import_a_module`
shows what program 14 looks like as two files.

## Not in M5

Each needs real programs that reached for it, recorded in
`programs/RECORD.md`:

- **Private names**, with `pub` or a naming rule.
- **`import "x" as y`.** Two imports with the same last part are refused
  for now; rename a file.
- **Importing single names**, `import "shapes" (Circle, Rect)`, to write
  them without the module name.
- **Dependencies from git,** pinned to a commit, as `CLAUDE.md` defers.
  A path whose first part contains a `.` (`github.com/...`) is kept for
  them, and refused until then.
- **Packages, search paths, and a module per directory.**
- **Re-exporting** a module's names from another module.

## For review

1. **Qualified names only** (`shapes.Circle(r)` even in patterns). It is
   one rule, and the same rule as `fs.read`. A match over an imported sum
   type is wordier than one over a local type. The alternative is
   importing named items unqualified, which is a second syntax with
   collision rules.
2. **Imported files hold only declarations and `let`s.** The
   alternative is Python's: an imported file's top-level statements run
   once on import. That makes importing a file visible, and makes order
   matter in ways the importer cannot see.
3. **The path has no `.fn`.** `import "stats.fn"` is refused with the
   fix, so there is one way to write it.
4. **No private names** until real programs need them.
5. **Messages qualify a type with its module only when it comes from
   another file,** so a one-file program's messages do not change.
