# M4: error messages, formatter, language server

Tooling for the language M3 finished. All three parts read what the lexer,
parser and type checker already produce; none changes the language. They
are built in this order, because the language server shows the messages
and runs the formatter.

Acceptance material lives in `examples/m4/`: `messages/`, `fmt/` and
`lsp/`, each with a README. It is written before the code
and wired into `go test ./...` as each part lands.

## Part 1: error messages that name the fix

The rule in CLAUDE.md is that every message says what is wrong and what to
write instead. M4 makes that checkable.

**Every diagnostic has a help line.** Today 28 of the type checker's
diagnostics and 18 of the runtime's have none (the inventory is below). A
test will fail if any diagnostic the suite produces has an empty help.

**The runtime's own checks are internal errors.** Almost every runtime
diagnostic is now unreachable, because the checker refuses those programs
first. Where one does fire, it is a bug in Fennic, and says so: "this is a
bug in Fennic, not in your program: the type checker should have refused
it". It names the program to report.

**The messages real programs ran into are fixed first.**
`programs/RECORD.md` lists them. Each is a case in `examples/m4/messages/`,
with the exact message expected:

| Case | Today | M4 |
| --- | --- | --- |
| `xs \|> len() == 0` | "expected the end of the statement, found `==`" / "put each statement on its own line"; in an `if`, "write the branch in braces" | names the precedence and the fix: `(xs \|> len()) == 0` |
| `topic.prefix: Str` in a record | "expected `:`, found `.`" / "give the field a type, like `topic: Str`" | a field name cannot contain `.`; use `topic_prefix`, or a `Map[Str, Str]` field to read such keys |
| `none -> ...` as a match arm | "expected a pattern, found `none`" | test with `x == none`, or default with `??` |
| `for (k, v) in pairs` | "expected a name, found `(`" | name one value, then take it apart with `match` |
| `sort_by_value` on a map of lists | help: "map the values to Ints, Floats or Strs first" | names `map_values`, which does that |
| `&&` | help: "use `match` on the condition" (stale since `and` exists) | write `and` |
| `\|\|` | help: "to handle a failure write `or`" (stale since step 2) | write `or`; for a failure, `else` |
| unhandled `int.parse(...)!` at the top level | help ends "`... else <fallback value>`" | a real fallback, from the checker's types: `else 0` |
| `len(3)`, `-"a"`, `1 with {...}` | no help | each names the fix |

**Not in M4:** rewording messages that already name a fix, and code actions
that apply a fix automatically.

## Part 2: the formatter

`fennic fmt file.fn ...` rewrites each file in canonical form.
`fennic fmt --check file.fn ...` changes nothing, prints the files that
are not formatted, and exits with 1 if there are any, for CI. There are
no options. A file with syntax errors is not formatted: its errors are
printed and it is left as it is.

**Line breaks are the author's.** The formatter never joins or splits lines
for length; there is no width. Where the author broke a pipeline, a list or
an argument list across lines, it stays broken. Where they kept a block on
one line, `{ a; b }`, it stays on one line. Within that:

- **Indentation.** Two spaces per level. A continued line, such as a line
  starting with `|>` or a field of a multi-line literal, is one level deeper
  than the line it continues.
- **Spaces.** One space around binary operators, `->`, `=` and `+=`, and
  after a keyword such as `if`, `not` or `fail`. One after `,` and `:`,
  none before. None inside `( )` and `[ ]`. One inside a
  one-line `{ }`, and between a record's name and its brace:
  `User { name: "Ada" }`. A map literal is written tight, like a list:
  `Map{"apples": 3}`. No space before `(` in a call, or before `[` in an
  index or type arguments.
- **Blank lines.** None at the start or end of a block or of the file,
  which ends with one newline. At most one between statements; the
  author's single blank lines are kept.
- **Trailing commas.** Added after the last element of a list, map, record
  literal or argument list that spans lines; removed on one line.
- **Match arms.** When consecutive arms are each on one line, their `->`
  line up, one space after the longest pattern.
- **Comments** are kept, with their text unchanged. A comment on its own
  line is indented like the code it precedes. Trailing comments on
  consecutive lines line up, one space after the longest code; a trailing
  comment alone gets one space.
- **Literals** are written exactly as the source had them: numbers,
  escapes, backtick strings, and the code inside `{...}` in a string.
- **Semicolons** stay where they separate statements on one line, followed
  by one space.

**What formatting guarantees,** each checked over every `.fn` file in the
repository:
- **The same program:** the tree before and after formatting is identical.
- **Idempotent:** formatting formatted code changes nothing.
- **No comment lost or reordered.**

**The repository is formatted.** Everything in `examples/`, `programs/` and
the docs' code is run through the formatter when it lands, so all of it is
a fixed point.

### The spec's programs

Four of the twenty programs in `docs/m0-spec.md` were not in canonical
form under these rules:

- **4 and 5:** a trailing comment preceded by several spaces.
- **6:** `User{name: "Asha", age: 31}`.
- **15:** match arms aligned further than the longest pattern.

`examples/m0` copies the spec text byte for byte, so the two rules
collided. **Decided:** the spec text of those four is reformatted when the
formatter lands, and the commit says why. `examples/m0` is not exempt.

## Part 3: the language server

`fennic lsp` speaks the Language Server Protocol (3.17) over standard input
and output: JSON-RPC 2.0 with `Content-Length` framing, Go's standard
library only. A client sends the whole document on every change.

| Feature | Method | Answer |
| --- | --- | --- |
| Diagnostics | `textDocument/publishDiagnostics`, after `didOpen` and `didChange` | Every lexer, parser, mutability and type error, in order. The message is the error, then a blank line, then `help: ...`. Severity is Error; the source is `fennic`. An empty list when the file is clean. |
| Formatting | `textDocument/formatting` | One edit replacing the whole document with its formatted text. No edits if it is already formatted, or if it has syntax errors. |
| Hover | `textDocument/hover` | For a name or a field, its type: `count: Int`. For a function or method, its signature: `fn greet(who: Str) -> Str`; for a built-in, at the types it is used with: `fn len(List[Int]) -> Int`. Nothing on keywords, literals or whitespace. |
| Definition | `textDocument/definition` | Where the name under the cursor is declared: a `let`, `var`, parameter, `for` variable, pattern binding, function, method, type, variant or record field. Nothing for built-ins. |

Also `initialize` (advertising those four capabilities), `initialized`,
`shutdown`, `exit`, `didOpen`, `didChange` and `didClose`. Any other
request is answered "method not found", and any other notification is
ignored.

**Positions.** LSP columns count UTF-16 code units by default, and Fennic's
count characters. The server converts both ways. If the client offers
`utf-8` or `utf-32` in `positionEncodings`, the server uses that instead.

**Broken files.** While a file has syntax errors, its diagnostics are
those errors, and hover and definition answer nothing. A diagnostics-only
answer is honest, and the parser's recovery does not keep enough of the
tree to type it. Hover on a half-typed file waits for a later milestone.

**It never crashes.** Every prefix of every example, sent as one edit after
another, must get a well-formed answer. A Go panic inside the server is
answered as an internal error for that request and logged; the server keeps
running.

**Acceptance:** scripted sessions in `examples/m4/lsp/`. Each is a list of
messages the client sends and the messages the server must answer with,
compared as JSON.

**Not in M4:** completion, rename, find references, semantic highlighting
and code actions.

## Decided at review

All recommendations were accepted:

1. **The spec's programs** are reformatted, not exempted (Part 2).
2. **Code inside `{...}` in a string is left as written** (`fmt/09`), so
   string literals stay byte for byte, and `"{a+1}"` stays unspaced.
3. **Match arms are aligned:** consecutive one-line arms put their `->`
   one space after the longest pattern (`fmt/05`).
4. **The top-level fallback for a record or sum type** is `T.default()`
   when that function exists, and otherwise the `err -> ...` handler form
   (`messages/README.md`).
5. **The client's tab options are ignored** (`lsp/04`): zero options
   includes the editor's settings.
